# ADR-0005: Unified Worker Runtime & Removal of the Session/Streaming Layer

## Status
Approved

## Context
A production-readiness audit of Milestone 28 (multi-provider workforce) found a critical, deterministically-reachable concurrency bug: `DepartmentOrchestrator` hardcoded exactly one member per department, disconnected from the real workforce `LocalProcessSupervisor` actually spawns. `TaskAssignmentEngine` always routed same-capability tasks to that one hardcoded member. The new dynamic mission planner (also M28) puts multiple same-capability tasks in one parallel execution batch. Combined, any LARGE/ENTERPRISE-scope goal dispatched 3 concurrent tasks to the same worker. `ReasoningCoordinator.activeByWorker` and each plugin's `activeChildProcesses` map were both keyed by workerId/sessionId — not by request — so concurrent same-worker executions silently overwrote and deleted each other's tracking, making cancellation non-deterministic and completion bookkeeping unreliable.

Investigating the root cause surfaced that "a worker" was represented by **five separate, unreconciled stores**, each owning a slice of what should be one entity:
- `WorkerRegistry` (via `LocalProcessSupervisor`): identity, pid, health metrics.
- `WorkerActivityRegistry` (M28): status, current task/file, workspace, history.
- `WorkerProviderAssignmentStore` (M28): assigned AI provider.
- `DepartmentMember[]` inside `DepartmentOrchestrator`: hardcoded roster + a load counter (`activeTasksCount`) that was incremented on assignment and never decremented anywhere in the codebase.
- `IRuntimeSession` (via `RuntimeSessionManager`/`SessionLifecycleManager`/`RuntimeSessionRegistry`): a "session" object, itself spawning a **second, independent decorative OS process** per worker (`node -e 'setInterval(...)'`) beyond the one `LocalProcessSupervisor` already spawns, whose only real remaining purpose was backing a fake, timer-based "streaming" simulation (`RuntimeSession.executeStream()`, literally commented "streaming simulation") that every plugin's manifest nonetheless advertised as a real `'Streaming'` capability.

Killing or stopping a worker only cleaned up the supervisor's own map; the other four were never touched, leaking an entry per store per removed worker indefinitely.

## Decision
Replace all five stores with **one domain entity, `Worker`, held in one store, `WorkerStore`**, and delete the session/streaming layer entirely rather than reconciling it.

- `src/v2/domain/employees/worker.ts` — a pure domain entity (no Node.js/child_process/fs imports) owning identity, process metrics, provider assignment, and a **single-flight `activeExecution` slot**. `beginExecution()` throws if the worker is already executing something; there is no way to represent "this worker is running two tasks" in the data model, because a real employee cannot do that either.
- `src/v2/application/worker/worker_store.ts` — the one in-memory registry of `Worker` instances. Every consumer (supervisor, department routing, task assignment, reasoning/execution, telemetry, CLI, TUI) reads and writes through this store. `remove(workerId)` is the single cleanup call a worker's removal requires.
- `DepartmentOrchestrator` no longer stores its own roster or a load counter. Department "membership" is a live filter over `WorkerStore` by department; "least loaded" is `!worker.isBusy` (derived from `activeExecution`, always current) instead of a counter nothing ever decremented.
- `TaskAssignmentEngine.assignPlanTasks` becomes batch-aware: when assigning multiple tasks from the same topological batch, it tracks provisional load *for that single call* so it spreads same-batch, same-capability tasks across distinct available department members when more than one exists, rather than piling them onto one worker. This fixes the root cause when workers are available. As a second, independent layer of defense — because `WorkerStore` is authoritative, not merely a suggestion — `ReasoningCoordinator` still rejects a second concurrent execution against a real, registered worker even if assignment ever produces one anyway (bug elsewhere, hostile input, future caller). A rejected request is retried by `MissionExecutionOrchestrator`'s existing backoff/retry policy, which already exists for this exact kind of transient failure — no new queueing subsystem was built for this.
- The **entire session/streaming layer is deleted**, not reconciled: `application/session/*` (`runtime_session.ts`, `runtime_session_manager.ts`, `runtime_session_registry.ts`, `session_lifecycle_manager.ts`), `infrastructure/transport/pty_transport.ts`, `contracts/iruntime_session.ts`. `IRuntimePlugin` loses `attachSession`/`detachSession`/`stream`; `execute()` is the only entry point and now takes `workerId` directly. Plugins track `activeChildProcesses` keyed by `workerId`, which is now safe precisely because `WorkerStore` guarantees at most one execution per worker at a time. `cancel(workerId)` kills the real tracked child process directly.
- Real multi-turn conversation continuity (`conversationSessionId`/`resumeConversation`, backing Claude's actual `--session-id`/`--resume`) is **unrelated** to the deleted `IRuntimeSession` class and is unaffected — it is passed straight through `execute()`'s payload as before.
- Planning reasoning (`AutonomousPlanner`, workerId `'emp-planner'`) is not a real registered `Worker` and is not subject to single-flight — asking the architecture/risk-analysis reasoning engine a question is not "an employee executing a task," and gating it identically would be semantically wrong, not just technically inconvenient.
- `DefaultRuntimeSelectionStrategy` (superseded by `WorkerAwareRuntimeSelectionStrategy` since Milestone 28, but left in place at the time) is deleted along with the pre-existing dead `ProcessSupervisor` and `WorkerRuntimeSkeleton` classes it was found alongside — per the standing instruction to remove obsolete implementations completely rather than leave multiple unreconciled answers to "what represents a worker" in the tree.

### Alternatives considered
1. **Keep the five stores, fix the map keys.** Rejected: this is the "wrap the old system" approach the current instructions explicitly forbid, and it does not remove the actual root cause (five sources of truth that can drift), only one symptom of it (the key collision).
2. **Build real chunk-by-chunk streaming instead of deleting it.** Considered seriously — the plumbing (`onOutputChunk`) already exists. Rejected for now: it is new feature work, not a fix, it is not exercised by the real worker-execution path at all today (`WorkerExecutionEngine` never sets `request.streaming`), and keeping a capability that is provably 100% simulated while calling it `'Streaming'` in every plugin manifest is exactly the kind of fakery this whole initiative exists to eliminate. If real interactive streaming is wanted later, it should be scoped and built deliberately against the real per-worker process the plugin already spawns, not resurrected from the deleted simulation.
3. **Full fair-queueing per worker (FIFO wait list) instead of reject-and-retry.** Rejected for now as over-scoping: the existing retry/backoff policy already provides adequate backpressure for the concurrency case this fixes, and a dedicated queue is a reasonable future enhancement once real usage patterns (not a hypothetical) justify it.
4. **Represent the department roster as configuration data instead of deriving it from `WorkerStore`.** Rejected: it is the exact same "second source of truth for who exists" problem this ADR removes, just moved into a config file instead of code.

## Consequences
- **One way to answer "who is this worker, what is it doing, what provider does it use, is it busy."** No cross-store drift is possible because there is only one store.
- **The concurrency bug is closed at its root** (assignment avoids doubling up when possible) and **backstopped** (the entity itself refuses a second concurrent execution).
- **Two fewer real OS processes spawned per worker** (the session layer's decorative process is gone) — real memory/process-table savings at the stated 1000-worker scale.
- **Breaking change, not backward compatible by design**: `IRuntimePlugin` implementers must drop `attachSession`/`detachSession`/`stream`; any caller of the CLI's `claudeStream`/`reasoningStream` commands loses them (they exercised only the simulation); tests asserting the old five-store shape are rewritten, not shimmed.
- **Multi-tenancy is still out of scope.** `WorkerStore` remains a single global registry, matching every other store it replaces — the "multiple concurrent users/projects" gap identified in the audit is unresolved by this ADR and remains a candidate for its own future milestone.
- **Streaming is a real capability regression** relative to what the manifests claimed (falsely) to support. If a real interactive/streaming use case emerges, it needs deliberate design against the real spawned process, not a resurrection of the deleted timer-based simulation.
